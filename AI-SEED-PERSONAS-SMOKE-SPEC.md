# Generador de perfiles sintéticos y smoke de IA

**Estado:** Draft; generador, matriz loopback, DB demo y launcher DevBar verificados. El 27-11 hubo 11 respuestas reales en un WebAPI aislado. Por instrucción expresa del usuario, la matriz completa se probó después contra el WebAPI ya levantado en `localhost:3001`, vía DevBar: 7 modos, 25 respuestas válidas y ningún fallo. El modo headless inicial produjo un challenge; al usar temporalmente headed con Xvfb, pasaron las rutas. Los casos live de fallo/timeout/cancelación y los contratos pendientes siguen abiertos.
**Rama/PR:** `feat/calendar-recipe-cooking` / #72 Draft. Sin merge ni publicación de datos.

## Objetivo

Crear un generador reutilizable de cuentas de prueba para usuarios solos y hogares con varios miembros, y una matriz finita que ejercite las entradas de generación de IA con perfiles sintéticos. Todas las cuentas creadas por el generador comparten la contraseña de prueba centralizada en el helper E2E existente; el generador no la duplica ni la incluye en capturas o informes.

Discrepancia verificada: `updateMemberSchema` no está conectado a una ruta; la API vigente de perfil es `PATCH /api/auth/taste`, con alergias como nombres simples y notas libres.

- `server/src/utils/ai-client.ts` y `server/src/utils/ai-function-providers.ts`: jobs actuales `receipt | recipe | multiple_recipes | recommendations | weekly_plan | shopping_photo | expiry_estimate | household_plan | assistant | product_image_search | connection_test`; asignaciones de proveedor para recetas, planificación, despensa/compra y hogar.

## Decisiones y límites

- Cubrir los valores válidos del contrato con una matriz pareada, no el producto cartesiano de todas las opciones: dos cuentas solas (cada una en un hogar de un miembro, porque el API vigente exige seleccionar/crear hogar), pareja de 2 miembros y hogar numeroso; variedad de niveles, objetivos, módulos, alergias, dietas y permisos.
- Crear correos sintéticos bajo `hogaria.test`, con identificador único de ejecución. No incorporar datos de personas reales.
- Crear cuentas mediante el helper de registro E2E existente, que aplica una contraseña común de prueba sin duplicarla en el generador. Mantener JWT y token WebAPI solo en memoria; no guardar credenciales, prompts ni respuestas en fixtures, logs, capturas o reportes.
- Mantener los valores `dietType`, tolerancia, ración y severidad solo como contexto sintético dentro de `taste.notes`, porque el API activo no persiste esos campos tipados. Verificar su lectura de vuelta; no escribirlos directamente a SQLite ni presentarlos como propiedades estructuradas del perfil.
- El generador no depende de una sesión humana previa: crea los usuarios sintéticos y obtiene sus JWT en la ejecución aislada. El smoke puede crear un bearer gestionado mediante `/admin/api/tokens` y lo elimina al acabar; no necesita iniciar sesión manualmente como usuario en WebAPI. La sesión del proveedor ChatGPT dentro de WebAPI es un estado distinto (estado read-only actual: `ready`) y se conserva como viene configurada; no se vuelve a autenticar ni se copia desde Brave.
- Evidencia de código WebAPI (consulta read-only 2026-11-27): `src/api/opencode/controller.ts` enruta `/v1/chat/completions` al proveedor `chatgpt`; los módulos de proveedor detectados son ChatGPT/Patchright. El schema solo admite el canal `chrome`, aunque permite `browserExecutablePath` personalizado; la guía canónica documenta el build Chrome instalado. `agenta.apiKey` se usa en `src/shared/observability/agenta.ts` para observabilidad, no como credencial de inferencia.
- Los smokes E2E y reales conservan una SQLite temporal dentro del directorio exclusivo de ejecución. La única excepción son los comandos explícitos de demo, que usan solo .tmp/ai-persona-demo/hogaria.sqlite con HOGARIA_DEMO_MODE=1; pnpm dev y pnpm dev:server nunca la seleccionan ni la cargan. No usar la SQLite normal del servidor DevBar.
- Los smokes reales son opt-in, secuenciales y con presupuesto máximo de llamadas explícito por flujo. Un error detiene la matriz; no hay reintentos ciegos ni bucles sin límite. Las suites repetibles simulan al proveedor.
- Cada modo live siembra una sola matriz por ejecución aislada y selecciona `solo-beginner`, `solo-allergy` o `family-owner` según la ruta. El permiso `HOGARIA_AI_SEED_GENERATION=1` se inyecta solo al proceso Playwright, no al servidor ni al navegador.
- Las propuestas no se aplican salvo que un escenario exija comprobar un flujo de confirmación; ese escenario usa datos y DB desechables.
- El WebAPI normal de DevBar no es una base de prueba: sus sesiones operativas pueden persistir el prompt completo y la respuesta en `session_events.content` (contrato de `docs/session-recording.md`). El smoke aislado usa DB WebAPI temporal además de la SQLite aislada de HogarIA. Revalidación read-only 2026-11-27 de `127.0.0.1:3001`: readiness 200 y proveedor `ready`, pero `requestLogging.enabled=true`, `captureDetails=true`, `sessionRecording.enabled=true` (`debugMode=false`, HTML diagnóstico desactivado). Por defecto, el harness falla antes de crear token o transmitir un prompt a esa instancia.
- Revisión posterior a la pregunta del 27-11: las únicas llamadas a `127.0.0.1:3001` fueron `GET /health/ready`, `GET /admin/api/chatgpt/session`, `GET /admin/api/runtime-controls`, `GET /admin/api/settings/session-recording` y `GET /admin/api/settings/diagnostic-html`. No hubo `POST /admin/api/tokens` ni petición de generación; no se esperaba una sesión nueva en `/admin/sessions`. La carga/revalidación de seeds fue contra HogarIA demo, no WebAPI.
- El 2026-11-27, un WebAPI temporal de loopback con SQLite propia y logging/captura/sesiones desactivados aceptó un bearer token temporal; `GET /v1/models` devolvió HTTP 200 y tres modelos. El token se eliminó y verificó ausente; proceso y DB temporal se limpiaron. Esto valida autenticación del cliente a WebAPI, no generación IA ni autenticación del proveedor.
- En un intento aislado distinto, `POST /admin/api/chatgpt/session/check` devolvió HTTP 503 `browser_unavailable` (`browser_launch_failed`: el runtime Patchright no encontró la distribución Chrome configurada). No se envió prompt ni generación, no se abrió Chrome y no se usó ni alteró el perfil Brave existente. El WebAPI normal de DevBar quedó intacto.
- Excepción autorizada por el usuario (27-11-2026): se ejecutaron los smokes con perfiles seed contra el WebAPI DevBar ya levantado en `127.0.0.1:3001`, sin arrancar otra instancia. Las acciones temporales apagaron request logging/captura y grabación de sesión, verificaron esos controles y los restauraron; el HTML diagnóstico siguió desactivado. Los logs consultados por DevBar se limitaron a metadatos estructurales y de ciclo de vida; no se guardaron prompts, respuestas ni credenciales en fixtures o artefactos.
- Receta: el WebAPI aceptó la solicitud en background (HTTP 200), pero el trabajo terminó `failed` con `errorCode=internal_error`; el job sintético registró `PROVIDER`, un intento y ningún resultado. La petición E2E esperó hasta el timeout de 270 s por la ventana de reintento manual. Conexión: el transporte también respondió HTTP 200 al aceptar el job, pero su estado terminal fue `failed`/`internal_error` en unos 3,7 s. Un HTTP 200 de aceptación no se considera una generación exitosa.
- Diagnóstico read-only por DevBar: el control reportaba `mode=inherit`, `effectiveHeadless=true`, Xvfb disponible en `:99`, ninguna página activa y coordinador idle. En los intentos fallidos, la telemetría estructural registró `challengeScript=1` y `composer=0`. Inferencia: la sesión autenticada (`ready`) no garantizaba que la UI de ChatGPT estuviera utilizable; la combinación apunta a challenge/estado de página incompleto, no prueba por sí sola la causa exacta de `internal_error`.
- Para verificarlo sin reiniciar WebAPI, se cambió el modo dinámico a `headed` mediante el endpoint de controles administrado desde DevBar; Xvfb ya estaba disponible y no había trabajo activo. La prueba enfocada de conexión pasó. Luego pasaron, en una acción DevBar con exit code 0, los 7 modos de la matriz: rutas core, generación de receta, workflows/Commons, plano de hogar, planificación de comidas, matriz del asistente y conexión. El WebAPI registró 25/25 respuestas de la matriz completas y una respuesta adicional del probe, sin fallos terminales.
- Al terminar, el modo volvió a `inherit` (`effectiveHeadless=true`), con cero páginas activas y coordinador listo. Verificación read-only confirmó que request logging/captura, grabación de sesión y HTML diagnóstico quedaron en sus valores originales. La DB persistente `demo (seeds)` no se reseteó ni se usó para las escrituras: cada run conservó su SQLite HogarIA aislada. No se abrió Chrome; Playwright usó Brave.

### Matriz objetivo de rutas live

Cada generación usa las cuentas/hogares del generador y una SQLite HogarIA aislada por run. Los tests repetibles usan un proveedor loopback simulado; el smoke real autorizado conecta esa app temporal al WebAPI DevBar ya existente y restaura sus controles de privacidad al finalizar. `profile` es el actor inicial; cuando se enumeran miembros, el escenario selecciona participantes de ese hogar para validar sus restricciones. El presupuesto cuenta respuestas reales de proveedor, no peticiones HTTP locales. Los tests deterministas de `product_image_search` usan su fixture de Commons y consumen cero completions de WebAPI.

No se reintenta un completion fallido automáticamente; se detiene el escenario y se limpian proxy, bearer propio y configuración temporal.

## Modo demo persistente

- La DB demo es un artefacto local ignorado por Git en .tmp/ai-persona-demo/hogaria.sqlite; nunca es una copia ni una ruta alternativa de data/hogaria.sqlite, server/data/ o la DB del WebAPI.
- pnpm demo inicia la app con HOGARIA_DEMO_MODE=1 y DATABASE_PATH fijado a esa ruta exacta; los comandos normales (pnpm dev, pnpm dev:server) mantienen su DB habitual. El arranque normal no carga fixtures ni cambia de modo por detectar el archivo.
- pnpm demo:seed crea las personas y hogares mediante peticiones HTTP a la API local de HogarIA, solo cuando el launcher del comando inició la API con modo demo y DB dedicada; no escribe directamente en la DB ni usa la base normal.
- pnpm demo:db:reset restablece únicamente esa DB y sus sidecars SQLite; rechaza rutas distintas, la DB abierta/en uso y la DB normal o del WebAPI. No detiene procesos ajenos.
- pnpm demo:regenerate es el flujo reproducible: restablece la DB demo propia, vuelve a sembrar los perfiles y recorre la matriz de generaciones con peticiones HTTP reales al WebAPI local. No acepta sustitutos loopback simulados, proveedores externos ni fallback silencioso; el destino debe ser el WebAPI local aislado, no el WebAPI normal de DevBar. El run tiene presupuesto/timeout finitos, aborta ante error y conserva solo estado sintético validado.
- El smoke real usa una configuración temporal de HogarIA que apunta al proxy loopback efímero. Al acabar cada escenario, incluso con fallo, debe borrar esa configuración mediante la API autenticada; conserva las salidas sintéticas generadas y no deja la URL efímera ni el marcador de clave en la DB demo.
- El 27-11 la primera regeneración real dejó esa configuración temporal activa en la DB demo. Se reprodujo leyendo solo metadatos, se añadió teardown por API y el E2E aislado de cleanup pasó; la configuración creada en aquella ejecución se eliminó por API. No se borraron las recetas, el ticket ni los trabajos generados.
- Antes de cualquier generación real, el preflight verifica origen loopback, identidad/readiness/autenticación del WebAPI y controles de privacidad; no cambia sus ajustes, toca su DB normal ni crea/borra credenciales ajenas. Si falta aislamiento o autorización, falla antes de transmitir prompts.
- Los unit/integration tests pueden simular proveedor, pero deben probar que los comandos demo rechazan simulaciones y que las generaciones demo llegan al WebAPI local real. Los artefactos de demo se quedan fuera de Git; no registrar secretos, prompts ni respuestas.
